description: "OPT-A fires a push notification on every card transaction within seconds of the transaction posting, to all retail cardholders, with no setup or opt-in required from the cardholder. The notification appears on the cardholder's lock screen and identifies the charge: time, amount, and merchant name drawn from the transaction record. The notification carries two inline actions: a confirmation action and a dispute action. Selecting the confirmation action dismisses the notification quietly with no further action. Selecting the dispute action opens the CS app directly to a purpose-built dispute screen, pre-filled with the transaction's date, amount, and merchant from the transaction record, and with the reason pre-selected as 'I did not authorise this charge'. The cardholder reviews the pre-filled detail, adds any additional context they choose to supply, and submits. The path from receiving the notification to submitting a dispute requires no navigation and no manual entry of the transaction fields the bank already holds. A cardholder who dismisses the notification or does not act on it can still find the transaction in the CS app's transaction list and initiate a dispute from the transaction detail screen using the standard path; the notification-assisted path and the standard path reach the same dispute screen. Notification frequency tracks the cardholder's own card activity: a cardholder who makes ten transactions in a day receives ten notifications. The pilot's first test is whether real-time awareness of every transaction changes the rate at which cardholders dispute unauthorised charges, relative to the pre-pilot baseline. The pilot's second test is whether notification frequency at cardholder activity levels produces engagement with the dispute action over the observation period or produces diminishing attention, measurable through opt-out rate and notification interaction rate stratified by cardholder transaction frequency. Default-on enrollment is the design decision that distinguishes OPT-A: all cardholders receive the notification without any activation step, separating it from KB's manual-activation model (ST2). The ePrivacy-compliant opt-out is always accessible: from within every notification and from the CS app's notification settings. Opt-out stops all transaction notifications immediately; re-enrollment from settings is available at any time. Before the first notification fires to any cardholder, an enrollment notice describes what they will receive, what the notification will contain, and how to opt out; this disclosure, delivered as an in-app message or onboarding step ahead of the first transaction notification, is the mechanism through which the default-on design addresses the ePrivacy consent requirement for push notifications. Opt-out and re-enrollment events are logged per cardholder with timestamps, creating an auditable consent record. Notification content is scoped to the three minimum fields required for the cardholder to identify the transaction and exercise the dispute action: time, amount, and merchant name from the transaction record. No partial card numbers, account identifiers, location data, or additional transaction metadata appear in the notification. This content scope is a design specification requirement addressing the GDPR personal-data-minimisation obligation for transaction-level content in a push notification; it is not a post-specification UI decision. The purpose-built pre-filled dispute screen is a design dependency of OPT-A: the dispute action must have a screen to open, and that screen is specified separately from the notification mechanism itself."

analyst_input: "Stage 6 needs the following to write the PRD. (1) Dispute screen specification: OPT-A opens a purpose-built pre-filled dispute screen. The PRD must specify whether this is a new screen built for the pilot, an adaptation of the existing transaction detail screen, or the ID-2 dispute flow reached through a new notification entry path. A9 states that ID-3 opens a dispute screen it does not itself build; the PRD is where that dependency becomes a specified component with its own requirements. (2) Notification delivery architecture: the latency requirement — notifications fire within seconds of a transaction posting (A8 step 1) — has engineering implications the PRD must constrain. What backend integration is required to receive a transaction event and dispatch a push notification within that window must be specified before implementation begins. (3) Enrollment notice design: the ePrivacy compliance design requires a disclosure step before the first notification fires. The PRD must specify the notice content, its delivery mechanism (in-app message, onboarding screen, settings prompt), and its sequencing relative to the first transaction notification. (4) Pilot measurement plan: OPT-A tests two questions. (a) Does real-time universal transaction awareness change dispute behaviour relative to the pre-pilot baseline? (b) Does notification frequency at cardholder activity levels produce engagement or diminishing attention over the observation period? The PRD must define the events logged (notification received, notification interaction, dispute action selected, dispute submitted, opt-out, re-enrollment), the comparison baseline for question (a), the stratification approach by transaction frequency for question (b), and the observation period. (5) Success measures — horizon, owner and kill criterion: the PRD Template requires all three for each success measure. For question (a), a 60 to 90 day observation period is implied by the design's need to compare pre- and post-notification dispute behaviour, but is not stated here and must be agreed before the PRD is finalised. The kill criterion for question (a) — at what absence of change the pilot is concluded — is not obvious from OPT-A's design and must be set by the Product Owner before the PRD is agreed. For question (b), the kill criterion is structurally implied: if opt-out rate reaches a level indicating that the notification is experienced as noise rather than signal at average cardholder activity levels, the universal design has failed its own stated test. The threshold is not stated here and must be set before the PRD is agreed. The owner for both success measures is unknown from this artifact. (6) Notification content specification: character limits for merchant name truncation when the name exceeds the notification display limit, handling of merchant names that are blank or ambiguous in the transaction record, and whether the notification format and inline action layout differ between iOS and Android. (7) Confirmation action logging: A8 step 1 specifies that the confirmation action dismisses the notification quietly. The PRD must specify whether this event is logged and under what processing basis, given that a cardholder-confirmed authorisation is a potentially useful signal for fraud detection. (8) Notification delivery failure handling: what the cardholder state is when a push notification cannot be delivered to a specific device (device offline, OS-level notification permissions revoked at the time of delivery), and whether delivery failures are logged against the cardholder's enrollment record."
